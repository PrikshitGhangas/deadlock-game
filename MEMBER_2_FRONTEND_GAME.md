# 2. Engine → UI relationship

The engine does not directly manipulate React components.

Instead, it returns step snapshots.

A snapshot contains information such as:

```text
event
operation
lockTable
wfg
dfs trace
cycle
blocked transactions
committed transactions
statuses
timestamps
metadata
explanation
```

React simply renders the current snapshot.

This makes the simulator deterministic and replayable.

---

# 3. Why step snapshots?

Suppose the simulation has 12 steps.

Instead of recalculating the entire simulation every time the user presses "previous":

```text
step 1
step 2
...
step 12
```

the engine has already produced all snapshots.

The UI can therefore:

```text
← previous
→ next
Home
End
Space = play/pause
```

without rerunning the algorithm.

File:


Nodes represent transactions.

Node shapes communicate status:


# 6. DFS animation

The WFG component reads the DFS trace generated by the engine.

Events:

```text

edge
backtrack

```

The component schedules animations.

Conceptually:

```text
visit T1
 ↓
follow T1 → T2
 ↓
visit T2
 ↓
follow T2 → T1
 ↓
cycleFound
```

The cycle edges are highlighted.

Important:

> Cytoscape does not perform the deadlock algorithm. It visualizes the algorithm's trace generated by the engine.

This distinction is useful in cross-questioning.

# 9. Game mode

The Game turns the student into the scheduler.

Instead of:

```text
engine chooses next transaction
```

the player chooses:

```text
which transaction executes next
```

Each card shows the next operation for a transaction.

---

# 10. Game state

A game state contains:

```text
level
transactions
LockManager
pending operations
completed operations
blocked operations
committed transactions
status
cycle
moves
wait count
hints used
score
```

The state is cloned before a move.

This makes game operations effectively pure:

```text
state + move → new state
```

---

# 11. How a game move works

Example:

```text
player chooses T1
```

The engine:

1. clones state
2. takes T1's next operation
3. executes it
4. checks for lock conflict
5. updates lock manager
6. builds WFG
7. checks cycle
8. calculates score
9. creates a snapshot
10. returns new state

If a cycle is formed:

```text
status = deadlock
score = 0
```

# 12. Hint system

The hint is more interesting than a simple "avoid this operation" rule.

For every currently available move:

```text
simulate move
↓
is resulting state winnable?
```

The engine uses exhaustive search.

Pseudo-logic:

```text
isWinnable(state):
    if won: true
    if deadlock: false
    if state already seen: return memoized answer

    for each available move:
        next = applyMove(move)
        if isWinnable(next):
            return true

    return false
```

Memoization avoids repeating identical states.

---

# 13. Why exhaustive search is acceptable

The game deliberately limits levels to very small state spaces.

The code comments target approximately:

```text
≤ 4 transactions
≤ 5 operations per transaction
```

This is not a production scheduler.

The goal is to give an exact educational answer:

> Does there still exist a winning schedule from here?

---

# 14. Hint scoring

Each hint costs:

```text
10 points
```

A normal wait costs:

```text
5 points
```

A successful no-wait completion receives a bonus.

This turns deadlock theory into a scheduling challenge.

# 15. Offline tutor

File:

```text
client/src/engine/tutor.js
```

It is intentionally deterministic.

Pipeline:

```text
student question
 ↓
normalization
 ↓
entity extraction
 ↓
intent matching
 ↓
resolver
 ↓
answer from actual simulation data
```

Example:

```text
"why did T2 get rolled back?"
```

The tutor identifies:

```text
intent = whyVictim
entity = T2
```

and retrieves the actual victim step.

---

# 16. Why call it an offline tutor rather than AI?

Because it is not a generative model.

It is a rule-based natural-language interface over the deterministic simulation.

Advantages:

- no API key
- no internet
- deterministic
- reproducible
- low latency
- grounded in actual run data

---

# 18. Why include the offline answer in the AI prompt?

The offline engine is the source of truth for simulation facts.

The LLM is mainly used to produce natural explanations.

This reduces the risk that the LLM invents:

- a transaction
- a cycle
- a step
- a victim

The architecture is effectively:

```text
deterministic engine = facts
LLM = explanation language
```

# 21. Important panel questions

### Does Cytoscape detect deadlock?

No.

The engine detects the cycle; Cytoscape renders it.

### Why React?

The application has dynamic state and many reusable UI components.

### Why keep engine separate?

Testability, deterministic behavior, reuse, and clean architecture.

### Why not let the LLM run the simulation?

Because simulation correctness must be deterministic.

### Can the tutor work offline?

Yes. The default tutor is entirely local.

### Is exhaustive game search scalable?

No. It is intentionally restricted to tiny levels.

# 22. One-minute speaking script

> My part focuses on the interactive layer. The simulation engine produces deterministic step snapshots rather than directly manipulating the UI. React consumes these snapshots and renders the input, visualization and explanation panes. Cytoscape visualizes the Wait-For Graph and replays the DFS trace generated by the engine, so visualization and algorithmic correctness remain separate. We also built a game mode where the student chooses the transaction scheduling order. Its hint system performs exhaustive search with memoization to determine whether a winning schedule is still reachable, which is feasible because the game levels are intentionally small. Finally, the offline tutor uses normalization, entity extraction and intent matching to answer questions from the actual simulation state, while an optional server-side LLM can provide more natural explanations.
